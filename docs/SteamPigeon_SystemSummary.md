## How this document is maintained

This file is the **canonical, agreed reference** for the Steam Pigeon system — the record of *what we currently agree is true*. Open questions and design tensions are debated and decided in **GitHub issues** (the working layer), and flow *into* this document only once decided:

- **Issues are the decision log.** Discuss in the issue; record the outcome as a comment beginning `DECISION:` and tick the chosen option under "Decision needed".
- **This doc is the source of truth for "what".** It is never edited to contradict a *decided* issue without a new decision — that rule is what keeps fixes from conflicting.
- **Decisions flow issue → doc via small pull requests** that reference the issue (`Closes #N`), linking the decision and the text change in history.
- **Load-bearing policy decisions are promoted to ADRs** in [`docs/adr/`](adr/) (e.g. the Priority-1 deployment policy, [ADR-0003](adr/0003-priority1-deployment-raw-baro.md)). The Appendix A items and the tracker below link to the issues; the ADRs capture the durable rationale.
- **Issue status** is visible via the `status: needs-decision` → `status: decided` → `status: in-doc` labels.

## 1. Overall Purpose

Steam Pigeon is a flight-tracking and recovery system for medium- to high-power model rockets. It exists to do three things, in order of importance: **fire the right recovery charges at the right moments, help the user find the rocket after it lands, and record enough data to understand and improve each flight.** Everything else — live telemetry, orientation visualization, voice prompts — is secondary to those goals.

The system is built from three cooperating devices:

| Component | Role | Platform |
|---|---|---|
| **Locator** | Flies onboard the rocket. Reads sensors, runs the flight state machine, fires deployment charges, archives flight data, and transmits status over LoRa. | STM32WL5MOCH6TR (integrated sub-GHz LoRa radio), C/C++ bare-metal super-loop |
| **Receiver** | Carried by the user. Bridges the locator's LoRa link to the phone's Bluetooth Low Energy. | STM32WL5MOCH6TR + external BLE module (UART/AT-command controlled) |
| **App** | Runs on the user's Android phone. Displays telemetry, location, and orientation; speaks status; configures the locator and receiver; downloads and visualizes archived flights. | Android / Kotlin / Jetpack Compose |

Data path: **Locator ⇄ (LoRa) ⇄ Receiver ⇄ (BLE) ⇄ App.** The locator and the app never talk directly; the receiver relays every message and appends receiver-specific status.

## 2. Priorities

The authoritative list — with stable IDs now decoupled from priority — is [SteamPigeonRequirements.md](SteamPigeonRequirements.md) §2; it is mirrored here with implementation status. As of 2026-06-18 air starts (FR-P13) enter at Priority 3, and the two fusion goals (FR-P8/FR-P9) are **Deferred** ([ADR-0005](adr/0005-retire-ekf-raw-primary.md), #13).

### 2.1 The governing policy: proven sensors over unproven fusion

The single most important cross-cutting rule in the requirements is this:

> **Known sensor capabilities must be prioritized over unknown or untested sensor-fusion algorithms when supporting Priorities 1 and 2, until the fusion algorithms have been thoroughly vetted through extensive model tuning and real-world flight testing.**

Concretely (NFR-1), **Priority 1 (deployment-critical altitude and velocity), Priority 2 (post-landing GPS), and the Priority-3 air-start tilt gate (FR-P13) rely on proven sources — raw baro, raw GPS, and the high-rate gyro strapdown (NFR-9)** — not on EKF-fused outputs. Velocity used for Priority 1 must come from a "proven source."

This policy is now **honored** in the current firmware: apogee moved to raw baro after the 2026-06-14 fused-velocity divergence, and PR #9 (merged 2026-06-18, ADR-0003) moved the **main-chute altitude trigger and physical-deployment sensing onto raw-baro-derived altitude/velocity** via the shared `SelectDeploymentSource()` ladder (#1, #2 — closed). With FR-P8/FR-P9 deferred, the EKF is being **retired from the real-time path** (ADR-0005, #13); the residual work is tuning the robustness-layer thresholds against archived flights (#10).

## 3. Architecture

### 3.1 Locator hardware (onboard)

| Function | Part | Notes |
|---|---|---|
| MCU + radio | STM32WL5MOCH6TR | Integrated LoRa sub-GHz transceiver |
| Barometer | MS5611-01BA | Primary altitude/velocity source. No hardware spike filter — filtering done in software. |
| IMU | ISM6HG256X | Dual-range accelerometer (low-g + high-g, auto-selected) + gyro |
| GPS | SAM-M10Q | u-blox M10, **I2C** interface (addr 0x42) — see Appendix A, Item 4. Configured on the RAM layer only, so the firmware re-asserts it in flight; dynamic platform model is scheduled by flight phase ([ADR-0017](adr/0017-gps-receiver-configuration-ownership.md)) |
| Data flash | MX25L6436F | 64 Mbit external flash for flight archival |
| Power switch | DRV5032 hall sensor + latch | Magnetic on/off; N vs S field distinguishes on/off, drives the RT9080-33 3.3 V regulator enable |
| Battery charger | BQ25185 | 1 A standalone linear Li-ion charger |
| Audio | PAM8904 piezo driver + buzzer | Power-on, arm/disarm, recovery beacon |
| Deployment | 4× TPS22950 load switches | Enabled/disabled via 2N7002K + DMP2021UFDF; BSS84 gates continuity sensing |
| Interfaces | USB-C | Configuration + archived-flight download |

**Shared SPI2 bus:** the MS5611 baro, the ISM6HG256X IMU, and the MX25L6436F flash share SPI2 and are serialized by a single owner (`SpiBus`). The GPS is **not** on this bus (it is on I2C). See Appendix A, Item 4 — the requirements outline states the GPS shares the SPI bus, which does not match the implementation.

### 3.2 Firmware structure (Locator)

The firmware is organized as a composition root (`Factory`) that owns and wires every subsystem. There is no RTOS — execution is a single bare-metal super-loop (§3.3). ST's `UTIL_SEQ` sequencer ships with the SubGHz framework but is compiled out (its only caller, `MX_SubGHz_Phy_Process()`, is gated by the undefined `MX_SUBGHZ_PHY_PROCESS`); the radio is serviced from IRQ callbacks instead. This choice is recorded in [ADR-0002](adr/0002-execution-model-superloop-vs-rtos.md). Modules:

- **`Factory`** — constructs and connects all subsystems, owns the main-loop entry points (`ProcessRocketEvents`, `ServiceBus`), and routes radio/UART callbacks. C linkage is exposed through `Factory_C_Interface` so the CubeMX-generated C `main.c` can call into the C++ world.
- **`Navigation`** (`RocketNav`) — owns the three sensors (`ISM6HG256X`, `MS5611`, `SAMM10Q`) and the `InsEkf15` EKF. Produces both a fused `NavSolution` and raw per-sensor samples. Handles on-pad calibration (ZUPT, gyro-bias freeze, AGL zeroing), mounting-frame calibration from the configured nose axis (default `X`; `Auto` falls back to cardinal-axis detection on each arm), GPS rate-limiting, and per-phase EKF tuning (`setPhase`).
- **`FlightManager`** — the flight state machine. Owns *all* event detection (launch, burnout, apogee/noseover, deployment, landing) and the deployment scheduler. Writes per-sample data and discrete events to the archive.
- **`Communication`** — LoRa message framing, CRC, and the windowed/parity flight-data transfer protocol.
- **`Archive` / `FlightArchive`** — flight-data logging to external flash, event statistics, metadata records, and the settings journal. Records include ~2 s of pre-launch data via a RAM ring in `FlightManager`, drained into flash throttled to ≤ 1 flash chunk per cycle so launch never overruns the 50 ms budget ([ADR-0007](adr/0007-prelaunch-ring-monotonic-clock.md)).
- **`Deployment`** — low-level channel firing, continuity sensing, and the remote deployment-test sequence.
- **`UserInteraction`** — USB-C console for configuration and data export (UART2, **921600 baud by default** for fast CSV archive export; operator-settable 9600–921600 per device, stored locally and never carried over the air — [ADR-0024](adr/0024-console-baud-and-sync-byte-recovery.md)).
- **`PowerManagement`** — battery-voltage ADC read, plus the `v` (settling profile of the BATTLVL node against the BATTRD edge, VDDA measured via VREFINT rather than assumed) and `h` (hold the load switch on ~10 s for metering) console diagnostics. See [bench-battery-diag.md](bench-battery-diag.md). The reading itself is enabled and sampled two service counts apart in `Factory::ProcessRocketEvents`, so `readBatteryMillivolts()` depends on a caller in another file having raised BATTRD ~100 ms earlier. The ADC self-calibrates once in `MX_ADC_Init` — without it `CALFACT` stays 0 and every conversion carries the die's raw offset. Measured 2026-08-08: `CALFACT` 82 on one board and 62 on another, i.e. ~20 counts (~16 mV) of per-die spread that was uncorrected on every unit, and an ~83-count floor on a grounded BATTLVL node that vanished once calibration ran.
- **`FaultLog`** (`Diag`) — persistent crash/hang diagnostics. Captures the Cortex-M exception frame + fault-status registers on a fault, the last checkpoint tag + uptime on a watchdog hang, and reset cause + boot count on a normal boot, into a `.noinit` RAM record that survives reset (NFR-10, [ADR-0008](adr/0008-watchdog-fault-log.md)). Kicks the IWDG once per loop.
- **Common** — `Types.hpp` (the shared data model), buzzer, RGB LED, static strings, formatting, device UID.

### 3.3 Processing model

- **Super-loop at 20 Hz.** `SAMPLES_PER_SECOND = 20` → a **50 ms** processing window. TIM17 raises a periodic flag; the main `while(1)` loop services it by calling `ProcessRocketEvents` once per window. A free-running 1 MHz TIM2 provides microsecond timing diagnostics (`CycleProfiler` / the `Diag::` segment API, read live from the console `t` breakdown — the per-sample `TimingDiag` capture was removed with ARCHIVE_VERSION 6, [#38](https://github.com/fschroer/steam-pigeon-locator/issues/38)), and — GPS-PPS-disciplined via `elapsed`/`Pps_GetTim2TicksPerSec` — is the trusted timebase for the NFR-9 strapdown dt **and the archive's monotonic flight clock** (`AdvanceMonotonicMs`, [ADR-0007](adr/0007-prelaunch-ring-monotonic-clock.md)): archived timestamps are true GPS-anchored elapsed time, not a 50 ms-per-cycle counter. PPS interval validation lives in `Pps_AcceptInterval` (`Rocket/Common/Src/PpsDiscipline.c`): a dropout of up to 9 s is reconstructed into a valid rate, and anything less recoverable is rejected so the clock **holds its last good rate** rather than being rescaled by the missed-edge multiple ([ADR-0007](adr/0007-prelaunch-ring-monotonic-clock.md) 2026-07-18 amendment, [#30](https://github.com/fschroer/steam-pigeon-locator/issues/30)). Whether a given record was continuously disciplined is tracked in RAM but **not yet exported** ([#31](https://github.com/fschroer/steam-pigeon-locator/issues/31)).
- **Watchdog (NFR-10):** the hardware IWDG is refreshed once per cycle from main-loop context (`FaultLog_KickWatchdog`, recording a checkpoint tag); a stalled loop resets the MCU and the tag/uptime survive in `.noinit` RAM for post-mortem. See [ADR-0008](adr/0008-watchdog-fault-log.md).
- **The high-rate (NFR-9) gyro strapdown rides this same 20 Hz loop without a dedicated ISR:** the gyro is batched into the ISM6HG256X FIFO at 480 Hz and drained+integrated (~24 samples) each cycle, decoupled from the loop rate by the FIFO depth. See ADR-0005 implementation note.
- **Timebase caveat:** `HAL_GetTick`/`HAL_Delay` are the RTC-based LoRaWAN TimerServer (overridden in `sys_app.c`; SysTick is *not* the tick source). Correct in production (~ms) but they freeze/jump under a debugger — use **TIM2** for any measurement while halted.
- **Budget target ~25 ms of the 50 ms window**, leaving headroom for jitter and future work (per the requirements).
- **Bus discipline:** *nothing* issues SPI from an ISR. The baro conversion ISR only enqueues transactions; `ServiceBus()` drains the queue in main-loop context every spin, so baro, IMU, flash, and console traffic can never overlap on the wire. This rule was introduced after a shared-bus collision between the baro ISR and flash logging produced non-physical altitude spikes and a false apogee.
- **ISR policy:** interrupts exit as fast as possible and queue any blocking work (UART RX bytes, SPI transactions) for main-loop processing.
- **Baro timing:** the MS5611 needs sequenced D1/D2 conversions; the conversion state machine is gated on elapsed time so a valid pressure value is guaranteed available within every 50 ms window.

### 3.4 Flight state machine

States (`FlightStates`): `WaitingLaunch → Launched → Burnout → Noseover → DroguePrimaryEvent → DrogueBackupEvent → MainPrimaryEvent → MainBackupEvent → Landed`.

**Re-arm without a power cycle.** Each arm (`Disarmed → Armed`) calls `FlightManager::PrepareForArm()` — a full flight-state reset (`ResetFlight()` returns the machine to `WaitingLaunch` and zeroes every per-flight variable and the record epoch) plus `ResetPreLaunchBuffer()` (clears the pre-launch ring); `Factory` also clears `datestamp_saved_`. So after a `Landed` flight a disarm→arm cycle re-initializes everything in place and opens a fresh record ([ADR-0007](adr/0007-prelaunch-ring-monotonic-clock.md) Decision 4, pairing with the [ADR-0010](adr/0010-archive-flash-robustness.md) record-reuse lifecycle) — no power cycle needed.

| Transition | Detection logic | Source |
|---|---|---|
| Launch ([ADR-0015](adr/0015-launch-detection-drop-rejection.md)) | Two OR'd confirmations, each vetoed if free-fall (< 0.3 g) was seen in the last 200 ms (drop-impact rejection): **dual-sensor** — accel ≥ 1.5 g **and** raw baro AGL ≥ `launch_detect_altitude`, sustained 80 ms; **or accel-only** — accel ≥ 5 g sustained 200 ms (the longer hold rejects a drop spike; the only path when baro is unzeroed/failed, and the one that catches a short-burn motor that coasts past the AGL gate only after burnout) | Fused accel (= raw IMU copy) + **raw baro** AGL |
| Burnout | Body accel < 1.5 g for 3 consecutive samples (150 ms) | Fused/raw IMU accel |
| Noseover/Apogee | Descending faster than 1.0 m/s **and** no new altitude max for 500 ms | **Raw baro** altitude + velocity (fused fallback only) |
| Drogue primary/backup | Time-since-noseover ≥ configured delay (tenths of a second) | Flight clock |
| Main primary/backup | AGL ≤ configured deploy altitude | **Fused** AGL (`nav_solution.altitude_agl_m`) |
| Physical drogue/main sensing | Velocity-change signatures | **Fused** vertical speed |
| Landed ([ADR-0018](adr/0018-landing-detection-quiescence-window.md)) | Raw baro \|vel\| below the quiescence threshold for a sustained confirm window — **the fused vertical-speed term is retired** ([ADR-0005](adr/0005-retire-ekf-raw-primary.md)); it reads 0 every sample and could only ever fire falsely. No AGL ceiling (landing may be uphill of the pad), so **duration is the only thing separating a landed rocket from a main-canopy inflation plateau**, which also reaches ≈ 0 m/s — see ADR-0018 for the validated 13–28 sample window at 1.0 m/s and why both constants must be re-validated together. Hard force-close at 8 min. On detect, ~2 s of samples are still logged in `Landed` before the record closes ([ADR-0007](adr/0007-prelaunch-ring-monotonic-clock.md) 2026-07-15 amendment). | **Raw baro** only |

**Deployment scheduling:** four channels, each independently mapped to a `DeployMode` (DroguePrimary / DrogueBackup / MainPrimary / MainBackup / Unused — an `Unused` channel is excluded from the firing schedule). The mode is settable from both the app and the locator's USB-C config menu (`UserInteraction` cycles the mode through all five values, including `Unused`). Channels fire one at a time — `DeployIfClear` queues any channel whose firing window overlaps another's, so only one charge is energized at a moment. Each firing records pre-fire continuity; after the configured `deploy_signal_duration` the channel is de-energized and post-fire continuity is recorded. Stats are bit-packed (mode / fired / pre-continuity / post-continuity) per channel.

### 3.5 Communication protocol

- **Two physical links:** LoRa (locator ⇄ receiver) and BLE (receiver ⇄ app). The receiver is a transparent relay that also injects its own channel, name, battery, RSSI, and version.
- **Framing:** 6-byte `PacketHeader` (`system_id` 0x44, `MsgType`, `msg_count`, CRC-16/IBM with a **fixed** seed `0xFFFF`). The CRC is an integrity check, not a secret — the receiver validates and re-computes it and cannot hold per-locator secrets, which is why connection authorization (below) uses a separate field. Max LoRa payload 255 bytes (radio length register is 8-bit).
- **Message types** (`MsgType`): startup, locator/receiver config-change requests, arm/disarm, prelaunch data (unarmed), telemetry data (armed), flight-metadata request/response, flight-data request/response + parity + ACK, deployment-test request/countdown, receiver-info request/response *(receiver-only, IDs 15–16)*, version request/info, flight-events *(ID 19)*, channel-survey request/response *(receiver-only, IDs 20–21)*, pad-alert snooze *(ID 22)*, locator-search request/streamed result *(receiver-only, IDs 23–24)*.
- **Telemetry split:** `PreLaunchData` (rich, sent while disarmed — includes raw + processed GPS, deploy config, battery, plus the locator ID + password `auth_tag` for connection authorization) vs `TelemetryData` (compact, sent while armed — fused NED velocity, body-to-NED quaternion, flight state, deployment stats). **`TelemetryData` carries the same `locator_id` + `auth_tag` pair**, added 2026-08-04: without it an app opened while the locator was already armed had nothing to authenticate and showed "No Locator" for the whole flight. The original "keep telemetry minimal for range" argument was retired on measurement — the pair costs 15.4 ms per second against ~877 ms of dead air, and payload length does not move the link budget at all, since sensitivity is set by SF/BW/CR ([ADR-0006](adr/0006-locator-connect-password.md)).
- **Connection authorization (FR-P14, [ADR-0006](adr/0006-locator-connect-password.md)):** `PreLaunchData` carries a cleartext `locator_id` (from the MCU UID) and a password-seeded `auth_tag` (two keyed CRC-16 passes over the base struct with `crc`/`auth_tag` zeroed; key = FNV-1a of the password, `0` = open). The receiver forwards both untouched. The app identifies the locator by `locator_id`, verifies `auth_tag` with the stored/entered password, and only **recognizes** (processes for control, enables commands) locators it is authorized for — challenging for a password on first contact with an unknown one and warning about conflicting traffic. The password is set **and viewed** only over the locator's USB-C console (stored plaintext in the locator-only runtime journal, never in the over-the-air settings). The app challenges for it on first contact with an unknown locator (on startup or a channel change) and warns about conflicting traffic. Enforcement is app-side (soft gate); locator config is additionally accepted only while Disarmed.
- **Command addressing (safety; [ADR-0020](adr/0020-targeted-locator-commands.md)):** every app→locator command carries `target_locator_id` immediately after the header, and the locator discards anything not matching its own UID **before any state change**. Without it, LoRa being a broadcast medium meant *every* locator on the channel obeyed *every* command: a channel change moved two locators at once and rewrote a bystander's whole `RocketPersistentSettings` (deployment modes, deploy delays, main altitudes), and **`ArmRequest` armed every disarmed locator on a shared launch channel**. `0` matches nothing, so an app build predating this fails closed. This is the half [ADR-0006](adr/0006-locator-connect-password.md) never had — that gate governs whose telemetry the app *acts on*, not which locators *receive* a command, and no app-side gating can fix a wire format with no addressee. Corollary worth applying to anything added later: once commands are addressed, every *response* is implicitly addressed too, but unsolicited broadcasts arrive from everyone, so anything derived from them must be gated on `locator_id`.
- **Interference detection ([ADR-0019](adr/0019-channel-interference-detection.md)):** the receiver appends `snr`, an idle-channel `noise_floor` and a `bad_frames` count to both broadcasts (receiver-appended, outside the authenticated region, so the locator is untouched); the app classifies. The decisive signal turned out **not** to be power: co-channel LoRa *displaces* rather than corrupts — capture means the receiver decodes the first preamble cleanly and never hears the second, so nothing fails a CRC and SNR stays pristine — while the app is meanwhile receiving and identifying the interfering locator by its `locator_id`. Power measurements are kept because they are the only way to see a **non-locator** emitter. An on-demand **channel survey** sweeps all 64 channels (fast strided coarse pass, then a full-broadcast-period dwell on five candidates including the home channel) and counts *decoded frames* per candidate, which is the only unambiguous test for "a locator is using this channel". Disarmed-only; the console traces it. **The channel is also measurable with no locator at all** (2026-08-11): `ReceiverInfo` — the one message the receiver sends without a locator involved — now carries the same `noise_floor` and `bad_frames`, and the app polls it every 2 s once the locator has been unheard for 5 s (not sooner: the floor is a drain-on-read peak, so an extra reader shortens every subsequent window and would bias the measurement down through the one or two broadcasts a distant rocket routinely drops). Before this, every measurement rode on a broadcast, so silence was unmeasurable and the verdict kept re-deriving itself from the last packet before the dropout — *"Interference detected"* latched permanently over a switched-off locator, and over a switched-off receiver. Evidence now expires after 3 s, `rssi`/`snr` ageing on a **separate clock** from the floor since the two no longer share a source. The subtle half: the two floors are **different statistics**. The receiver samples inside the safe window while the locator transmits and *continuously* once it goes overdue, so the silent regime is the peak of several times as many samples and reads higher — and mixing them was unrecoverable, because a minimum-keeping baseline can never rise to meet the busier regime and an absolute threshold has nothing that can bring it back down. One baseline per regime, and no absolute test on polled readings. **Breaking receiver↔app wire change** (`ReceiverInfoMessage` 27 → 30, app payload 21 → 24), and a nastier one than most: the app frames this message by exact length *before* checking its CRC, so a mismatched pair desynchronises the framer rather than failing a check, and [ADR-0012](adr/0012-app-ble-connection-health-probe.md)'s watchdog then reconnects in a loop.
- **Channel plan and Part 15 compliance ([ADR-0025](adr/0025-lora-channel-plan-and-part-15-compliance.md), Proposed — nothing decided, nothing implemented):** the link runs `902_300_000 + ch × 200_000` Hz for channels 0–63 (902.3–914.9 MHz) at SF7/BW125/CR4-5 and 22 dBm — which is the **LoRaWAN US915 uplink plan verbatim**, inherited rather than designed; its 914.9 ceiling is an artifact of LoRaWAN's uplink/downlink split, so roughly half the band is unused for a reason that does not apply here. Two findings. **(1)** A *fixed* 125 kHz carrier fits neither Part 15.247 route: digital modulation requires a 6 dB bandwidth ≥500 kHz (15.247(a)(2)), and FHSS requires ≥50 hopping frequencies at ≤0.4 s average occupancy per 20 s (15.247(a)(1)) — and the 64-channel plan exists *precisely* to satisfy that ≥50 rule, so the artifact was kept and the rationale discarded, the same shape of error [ADR-0019](adr/0019-channel-interference-detection.md) records four times. **(2)** Spacing is not the binding constraint; **displacement** is. Co-channel capture does not corrupt, and it does not average out — two locators at ~1 Hz sit in a phase relationship that drifts over *hours* if free-running and not at all if GPS-disciplined, so a collision is one working link and one dead one for the whole session, with no measurable symptom. Two routes: **BW500/SF9** (identical symbol time so every ADR-0009 timing constant is untouched, ~1 dB sensitivity cost, but only ~40–48 channels — *worse* collision odds than today) solves compliance only; **FHSS** solves displacement too and is the only option here that does, but couples the RF link to the GPS fix — and the receiver has no GPS, while the locator has a SAM-M10Q and [ADR-0007](adr/0007-prelaunch-ring-monotonic-clock.md)'s disciplined clock. Which route is preferred turns on expected flight-line density, and the ADR deliberately leaves it open rather than letting the cheaper option decide a product question. Also open: every locator ships on **channel 0** (`default_settings_` value-initialises it), which is the conflict source Eggtimer names as dominant in their own fleet.
- **Flight-data transfer ([ADR-0009](adr/0009-flight-data-transfer-reliability.md)):** archived flights are downloaded as a windowed burst (`kWindowSize = 8`, a whole multiple of `kParityGroupSize = 4`) with a parity packet per group for single-packet loss recovery, plus a deferred cumulative-ACK bitmap so the ACK is sent only when the locator's radio is idle. `kRetxTimeoutMs` (7000 ms) is sized to exceed the full burst so packets awaiting their deferred ACK aren't retransmitted mid-burst. Sample data is **delta-compressed** (48-byte base header + 24-byte per-sample deltas) to fit many samples per packet. Each `FlightData`/`FlightDataParity` frame is delimited on the wire by its **exact length derived from the header** (not by buffer size), so bursted or BLE-fragmented packets each pass the per-frame CRC-16 individually. `packet_count == 0` is a reserved header-only **"no data" marker** for an empty record. The locator returns to normal PreLaunchData transmission on the app's `DisarmRequest` (leaving the screen); short idle/active timeouts remain only as a disconnect safety net.
- **Profile altitude is raw baro.** The delta-compressed `base_altitude_m` / `d_alt_0p1m` fields carry `FlightSample::raw_baro_altitude_agl`, **not** `fused_altitude_agl` — the app's flight-profile chart plots the altitude the deployment decisions were actually made on ([ADR-0003](adr/0003-priority1-deployment-raw-baro.md), [ADR-0005](adr/0005-retire-ekf-raw-primary.md)). The archive still stores both columns per sample; the fused pair is the live EKF's observational output ([ADR-0013](adr/0013-realtime-ekf-fpuless-covariance-heuristics.md)) and reaches a human only through the locator's USB-C CSV export.
- **Flight events (`FlightEvents`, ID 19):** the `FlightMetadata` list message carries only what identifies a record (timestamp/apogee/flight time) for all 10 slots — a full event set per slot would not fit a 255-byte frame. So the locator sends a separate per-record summary for the **one** record the app asked for, transmitted (twice, best-effort, unacknowledged) during the pre-transfer guard window ahead of the first data packet. It carries the 11 archived event timestamps plus a present-mask, the raw-baro apogee, and the four deployment-channel stat bytes (mode / fired / pre- and post-fire continuity). Only event *times* are sent: the app derives each event's altitude by matching its timestamp to the nearest sample in the profile data it receives, so a chart marker always lands exactly on the plotted trace. Losing the summary costs only the chart's event markers — the data transfer is independently ACKed.

### 3.6 Receiver

Same STM32WL5 MCU. On boot it configures an external BLE module over UART using an AT-command sequence (command mode → enable BLE broadcast → set name from settings → set BLE address derived from the chip UID → reset). It relays LoRa↔BLE traffic, answers receiver-info and version requests, shows charge/BLE/comms status on an RGB LED, and offers its own USB-C configuration console (`UserInteraction`) and persistent settings (channel, device name, console baud). It uses a smaller data flash (MX25L4006E) for its settings journal. Console input is queued by the RX callback and handled from `Service()` rather than in interrupt context — required so that adopting a detected baud rate can re-init USART2, which cannot be done from inside that peripheral's own interrupt, and which brings the receiver into line with the ISR policy above that the locator already followed.

Forwarding app→locator commands is timing-aware (half-duplex collision avoidance): while the locator transmits periodically (PreLaunchData/Telemetry) the receiver forwards only in a safe window just after a received periodic message; once the locator is in **flight-profile mode** (a `FlightMetadata`, `FlightEvents`, or `FlightData` frame seen ⇒ locator quiet and listening) it forwards immediately, and during a data burst it defers the app's `FlightDataAck` until the burst goes silent ([ADR-0009](adr/0009-flight-data-transfer-reliability.md)).

**Two fields in `LocatorCfgChgRequest` are reserved ([ADR-0028](adr/0028-app-does-not-transmit-unconfirmable-settings.md)):** the message carries the whole `RocketPersistentSettings` struct, but `launch_detect_altitude` and `deploy_signal_duration` are no longer applied by the locator — it restores its own values after copying the message, and the app fills both slots with the firmware defaults. Neither field rides in `PreLaunchData`, so the app cannot read back what the locator holds for either, and it confirms a config change by whole-object equality against a config rebuilt from the next broadcast; sending them therefore made every change report failure while succeeding, and overwrote both on every change including a plain channel move. The slots stay occupied so `lora_channel` keeps the offset the receiver reads it at (ADR-0011 below), and every size assertion still holds at 45 bytes. Both fields are now fixed at their defaults on any device — the USB-C console never set them either.

**Following a locator channel change ([ADR-0011](adr/0011-locator-lora-channel-from-app.md)):** when the app changes the *locator's* LoRa channel (from Locator Settings), the receiver forwards the `LocatorCfgChgRequest` to the locator on the **old** channel and then, once that transmit has completed, switches its own channel to match so the link is preserved. The switch is deferred to main-loop context after `OnRadioTxDone` — changing RF frequency between `Send()` and TxDone would corrupt the very forward the locator needs. This is distinct from a receiver-only `ReceiverCfgChgRequest` (Receiver Settings), which retargets the receiver to a *different* locator already on another channel.

### 3.7 App

Android / Kotlin / Jetpack Compose, organized around a `RocketViewModel` and a set of `StateFlow` repositories (`FlightDataRepository`, `BluetoothManagerRepository`). Screens include: live **Flight Map** (with TTS status callouts), **Download Maps**, **Export Flight Path**, **Flight Profiles**, **Locator Settings**, **Receiver Settings**, **App Settings**, **Deployment Test**, and a **Device Picker**. A `Compass`/heads-up view converts the telemetry quaternion into inclination and compass heading to point the user at the rocket. BLE is handled by `BluetoothService` / `BluetoothConnectionManager`. User preferences persist via a Proto DataStore. (The unused USB-serial path and its `SerialManager` were removed 2026-07-16; the locator's USB-C link is used from the desktop tools, not the app.)

**Map ([ADR-0014](adr/0014-maplibre-offline-satellite-maps.md)):** the map is **MapLibre Native**, not Google Maps — Google's SDK exposes no offline API, and recovery happens where there is no cell signal. Satellite tiles for a launch site are cached as MapLibre **offline regions** (`ui/OfflineMapManager.kt`) and the live map renders from them with no connectivity; the map layer itself lives behind `ui/MapLibreCompat.kt`. The rocket marker and accuracy ring carry a **three-state trust color** (`RocketMarkerState`): green = live, **gray** = link healthy but the locator reports GPS health other than `Ok` (position is latched, not current), red = no recent packet. Link age is evaluated first, since with no recent packet the reported `gpsStatus` is itself stale. A degraded fix is *grayed, never hidden* — removing the last-known position from the screen would take away the only thing left to walk toward ([ADR-0017](adr/0017-gps-receiver-configuration-ownership.md)). **Release blocker:** no currently wired tile provider permits permanent offline caching (Mapbox requires its own Mobile SDK and caps caching at 30 days; Esri and MapTiler Cloud restrict bulk caching) — the wired providers are evaluation-only, with public-domain NAIP imagery the identified clean path. See ADR-0014 before shipping.

**Distance and bearing plausibility ([ADR-0022](adr/0022-distance-bearing-plausibility.md)):** the app will not quote a distance it cannot stand behind. Two tests. A distance beyond **100 km** is impossible on its face — telemetry arrives over LoRa to a receiver that is in the user's hand, so a packet arriving at all bounds the locator to radio range; this applies to the displayed figure and the spoken recovery bearing alike. Below that, a reading taken with **no fix** (fewer than 4 satellites, or non-`Ok` GPS health) is judged on whether it *jumped*, not on being fixless — a locator that loses its fix keeps reporting the last position it did measure, and that stale distance is the recovery aid, so it stays. The jump allowance is a **ground-speed** budget (the distance is a haversine with no altitude term, so a Mach 5 boost is Mach 5 straight up and barely moves it), accumulated per update at the bound for the current flight phase: 400 m/s boost and coast, 200 m/s descent, 5 m/s on the ground. Bearing shares the verdict — the AR locator marker, its off-screen edge arrow and both HUD gauge pointers are suppressed with the distance, since they come out of the same vector and an overlay is an instruction rather than a readout. **What is withheld is a derived figure, never the position:** the rocket marker keeps rendering under the trust colors above, which is the grayed-never-hidden rule, not an exception to it. The reading that prompted this was 779070 m with zero satellites.

**Heading: true north, and compass trust ([ADR-0023](adr/0023-app-heading-true-north-and-compass-trust.md)):** the phone's heading is converted from magnetic to true north with `GeomagneticField` before anything consumes it — the correction lands on the **device** azimuth, not the locator bearing, because MapLibre's camera bearing is true-north referenced too and correcting the other side would have fixed the AR overlay while leaving the rotated map wrong. Without it both the overlay and the map carried a standing error equal to the local declination, **+15.0°** at the sites this is flown at; a bias, not noise, which is why it read as "the compass is a bit off" rather than as a bug. Calibration status is taken from **both** `TYPE_MAGNETIC_FIELD` and `TYPE_ROTATION_VECTOR` accuracy, worst-of whichever have actually reported, because which one is alive is a property of the device and reverses between them: on a Pixel 9 Pro XL the magnetometer reports and the fused sensor never fires, on a Moto G 5S exactly the other way round. A source that has never spoken contributes nothing rather than contributing `HIGH`, so it cannot outvote a live one. Single-sourcing this — from either sensor — leaves the warning unreachable on half the hardware while still looking like a working feature, which it did twice before landing here. A **third** source covers devices where neither flag is usable at all — which is **two of the three measured**: the Moto G pins the rotation vector at `HIGH` under a magnet and never fires the magnetometer, and a Pixel 3 XL never fires either one, so there the magnitude test is not a fallback but the only signal there is. It is the **total field magnitude**, judged against the 22–67 µT the Earth can actually produce, which needs no cooperation from the OEM because a magnet cannot hide from the arithmetic. Devices rest at 50–53 µT measured, ~17–20 µT below the 70 µT ceiling, and a magnet peaked at 106 µT. It detects interference, not miscalibration — a stale hard-iron offset rotates the heading while magnitude stays plausible — so it joins the worst-of verdict rather than replacing the flags. `FieldMagnitudeTest` covers the classification. That raw signal chatters under interference (`UNRELIABLE`↔`LOW` in as little as 30 ms, against zero transitions in 25 s at rest), so a degraded reading publishes immediately and is held 3 s past the last bad one; recovery is the only thing that waits. `LOW` raises the on-map figure-eight prompt, `UNRELIABLE` additionally suppresses the AR marker through the same [ADR-0022](adr/0022-distance-bearing-plausibility.md) gate an implausible position uses.

**Closest map zoom (App settings, z18–z22, default z20):** bounds what **auto-zoom** frames to, and nothing else — the map sets no `setMaxZoomPreference`, so pinch is unaffected. It exists for GPS error, not tile supply: auto-zoom fits a box around the phone and the rocket, and at close range that box is mostly the two receivers' combined error, so it swings fix to fix and the fitted zoom chases it. The limit is applied inside the camera controller's Kalman filter (`MapCameraController`), not on the map — clamping the camera alone would leave the filter tracking the swings above the limit, calm-looking until one dropped back below and the map lurched. Range and default are constants, deliberately not derived from `SatelliteProvider.maxOfflineZoom`, which is a storage-driven *download* cap rather than a statement about available imagery. Stored as `optional int32` so "not chosen" stays distinct from a level.

**Auto-center deadband:** the same GPS error that makes auto-zoom pump also moves the point auto-center frames to, so the camera follows a latched **anchor** rather than the live target and re-latches only once that target has drifted past a distance derived from what the two receivers report about themselves — `hacc` from the locator (the figure drawn as the accuracy ring) and `Location.accuracy` from the phone. The band is `2·√2·σ_target`, clamped to 5–40 m: σ_target is **half** the combined error when both fixes are framed, because the camera targets the midpoint between them and a midpoint moves half as far as the points it is drawn from; the √2 is there because the anchor being measured against is itself one noisy sample, so what has to clear the band is the difference of two independent draws; the 2 makes it 2σ rather than 1σ. Deadbanding the **anchor** rather than the filter output is what makes it settle — skipping the filter step whenever the live target is within the band of the *camera* never converges, since the camera stops a full band short and then chatters on the boundary. The anchor is dropped on a gesture and on any camera-control tap, both of which mean "center now". Field-verified against a stationary locator: the map center held while the reported position wandered ~0.8 m. The band is then **capped at the fraction of the visible width that the bounds fit reserves as margin** outside the two markers — the statistical band knows nothing about zoom, and framed a few meters across it comes out wider than the viewport, which put a marker off screen in the field. Spending the fit's own margin on center drift is exactly the slack that exists to be spent.

**Auto-zoom deadband:** the same treatment for the zoom, whose input is the *separation* between the two fixes rather than the midpoint. Two differences from the centering band, neither cosmetic: no halving, because separation is a difference between the fixes and both errors land on it at full weight; and the conversion runs through the log, since zoom is logarithmic in separation — σ_zoom = σ_separation / (D·ln2). That is what makes the band self-scaling, and why deadbanding separation in meters could not work: at recovery range the required band is wider than the separation itself. Clamped to 0.25–1.5 zoom levels, the ceiling earning its place because the honest statistics say a fit whose separation and error are comparable should never move at all, which would leave the map framed for 30 m while the user stood 5 m away. The anchor holds the **unclamped** fit while the filter output stays clamped to the closest-zoom limit, so like compares with like. **The closest-zoom limit does not substitute for this** and it is worth being exact about why, since the setting looks as though it should: the limit binds how far *in* the fit may go, and these swings happen at and below it. Zoom recovered from the rendered scale bar across four captures read 20.57, 20.46, 20.01, 19.96 against Dist of 6, 7, 11, 11 m — tracking continuously, which a clamped value cannot do.

**The center banner pulses only when escalated:** `PulsingText` drives an infinite alpha transition, which redraws on every display frame for as long as it is visible — so pulsing the ordinary white "Disarmed" / "No GPS" states pinned the map screen at the panel's maximum refresh for the whole pre-flight wait. Measured on the map with live telemetry: **1220 rendered frames per 10 s and 131% of one core while pulsing, 261 frames and 114% static.** The residual is the compass rose redrawing at the rotation-vector sensor rate (~60 ms), plus telemetry and camera writes. Beyond the power cost, the [ADR-0021](adr/0021-arming-gates-pyro-only.md) Decision 5 argument applies to the pulse itself: motion through every ordinary state trains the eye past the escalation it is reserved for. Red `Alerting` and yellow `Snoozed` pulse; white does not. **"No Locator" left the center banner entirely** (2026-08-11) and now fills the locator-name slot on the status panel, beside the rocket icon whose satellite count and battery have gone blank with it — the row explains its own emptiness instead of pushing the explanation to the middle of the map, and the center banner is left for states of a rocket the app is actually hearing from. `PulsingText.pulse` deliberately has **no default**, so each call site must state its intent, and the transition is not constructed when static — an unread animation still keeps the frame clock subscribed.

**Logical vs device pixels at the map boundary:** MapLibre reports zoom in **logical (dp)** pixels — `metersPerDp` — and anything comparing a ground distance against a real count of screen pixels must divide by the display density first (`metersPerDevicePx`). Getting this wrong is silent and self-consistent, so it bit twice from one root: the scale bar multiplied meters-per-logical-pixel by `width.toPx()` and overstated every distance by the density (measured at 2.43× on a 2.25-density phone, against captures comparing the separation the bar implied with the `Dist` printed in the same frame), and the centering deadband's viewport check was calibrated with the same mistake, so it passed while believing half the screen was 15 m when it was nearer 6.7 m. **Density 1 is the only case where the two units agree**, which is why an emulator will not reveal it. The bounds-fit padding is likewise a *fraction* of the viewport rather than a fixed pixel count: at 300 px per side it surrendered 60% of a 1008 px-wide screen before framing anything, leaving the markers in a fifth of the display.

**Two message clocks:** `RocketState.lastMessageTime` is stamped by pre-launch *and* telemetry — link liveness, which is what almost every "are we still hearing it" gate wants. `lastPreLaunchDataTime` is stamped by pre-launch only, and is the correct clock for anything carried by just that message. Today that is the **battery levels**, which the locator stops sending at launch: gating them on the shared clock (the field was called `lastPreLaunchMessageTime`, which read as a promise it never kept) kept both gauges lit for the whole flight showing the charge from the pad. The gauges now clear at launch and return when pre-launch messages resume, after landing and re-arm.

**Coordinate hand-off:** the locator's lat/lon row on the stats panel is tappable, firing a `geo:` intent so the OS offers whatever mapping apps are installed (`<queries>` entry required for the pre-flight `resolveActivity` check on API 30+). Gated on the same plausibility verdict as the distance — a position the app will not quote is not one it will hand to a navigation app. Useful only with an offline-capable maps app installed and the region downloaded, which the user manual says out loud: the hand-off works with no signal, but Google Maps opens to a blank screen at a launch site.

**Where the drawn flight path stops:** the live track accumulates from launch until the app judges the flight over — either the locator reports `Landed` ([ADR-0018](adr/0018-landing-detection-quiescence-window.md)) or descent telemetry reaches the same imminent-touchdown test the landing callout speaks on. After that the path is frozen, with one exception: the locator's **first** `Landed` fix is still drawn, because it is the locator's own account of where the rocket is lying and it corrects an inference made from the last fix before a dropout. That fix ends the recording for the flight; only the next launch or the map's manual reset resumes it. The rocket marker keeps tracking live throughout — this stops the track being *extended*, and never removes anything already on screen, which would run against the grayed-never-hidden rule above. **The locator's landing verdict is therefore load-bearing for the app's track, not just for the flight record:** a false landing (ADR-0018 records two, one at 66 m AGL mid-descent) now truncates the drawn path at the same point it truncates the archive, where the app's live track previously ran on to the ground and was the only surviving trace of the back half of that flight.

**BLE connection health ([ADR-0012](adr/0012-app-ble-connection-health-probe.md)):** because Android can report a dead GATT link as connected (an OS-cached "phantom"), a watchdog verifies liveness after the link reaches `Ready`. It does **not** treat GATT silence as a dead link — a healthy receiver relays nothing whenever the locator is quiet (powered off, on the pad, out of range). Instead, each 10 s silent window sends a `ReceiverInfoRequest` (which the receiver answers on its own behalf, independent of locator activity); the link is reconnected only after three consecutive probes go unanswered (~30 s). When the locator is actively transmitting, no probe is sent. This replaced an earlier tear-down-on-silence watchdog that looped disconnect/reconnect whenever the locator was idle.

## 4. Features

### 4.1 Locator
- Autonomous flight detection and four-channel recovery deployment with primary/backup roles and per-channel continuity verification.
- On-pad calibration: zero-velocity update, gyro-bias estimation and freeze at ignition, AGL zeroing, and mounting-frame calibration re-run on every arm and on a pad settle — from the configured nose axis (default `X`), or by cardinal-axis detection when it is set to `Auto`.
- 15-state INS EKF with per-flight-phase Q/R tuning; optional baro dynamic-pressure ("pitot") correction.
- Full flight archival to external flash with discrete event timestamps and per-flight metadata; downloadable over LoRa or USB-C. Records prepend ~2 s of pre-launch data and are timestamped on a GPS-disciplined real-time clock (record starts at ~0 ms, launch at ~2000 ms — [ADR-0007](adr/0007-prelaunch-ring-monotonic-clock.md)).
- Robust archive lifecycle ([ADR-0010](adr/0010-archive-flash-robustness.md)): the flash is reset to a known state at every boot (so archived data survives a debugger/flash/watchdog reset without a power cycle); a flight that never landed is still recoverable (chunk-scan without a close trailer); an arm→disarm-before-launch→re-arm reuses the same record (durable across reboot) instead of consuming a slot; and USB-C data-menu commands reclaim empty "ghost" records or fully erase the archive for a structure change.
- Automatic hang recovery (IWDG watchdog) with persistent crash/hang diagnostics preserved across reset (NFR-10, [ADR-0008](adr/0008-watchdog-fault-log.md)).
- Audio cues for power-on, arm/disarm, and recovery.
- LoRa telemetry (prelaunch + in-flight), remotely commanded arm/disarm and deployment test.
- USB-C configuration and data export at 921600 baud by default (settable per device, [ADR-0024](adr/0024-console-baud-and-sync-byte-recovery.md)), including a USB-C-only connection password that authenticates the locator's broadcasts (FR-P14).

### 4.2 Receiver
- Transparent LoRa↔BLE relay with message-level forwarding.
- Injects receiver channel, name, battery, RSSI, and firmware version.
- Status LEDs for charging, BLE connectivity, and communication.
- USB-C configuration; persistent channel/name settings.
- Automatically follows the locator's channel when the app changes it, so the link is preserved without manual receiver reconfiguration ([ADR-0011](adr/0011-locator-lora-channel-from-app.md)).
- Measures link quality (SNR, idle-channel noise floor, failed-frame count) and surveys the band on request, tracing both to the USB-C console ([ADR-0019](adr/0019-channel-interference-detection.md)).
- Searches named channels for a locator on request and streams one result per channel, tagged `[search]` on the console ([ADR-0029](adr/0029-locator-search-candidate-channels.md)). The survey hunts quiet; this hunts a rocket, and the two cannot share a sweep — the survey's confirm phase dwells on the *quietest* candidates, which is the last place an active locator will be.

### 4.3 App
- Live telemetry and flight-state display.
- Signal readout with RSSI and SNR, and an interference verdict that stays silent at range — a distant rocket at apogee sits near the SF7 demod floor, so an SNR-only alert would fire on every healthy flight ([ADR-0019](adr/0019-channel-interference-detection.md)).
- **Version stamp** (2026-08-26): the app carries the same `YYYY.MM.DD-<git describe>[-dirty.HHMMSS]` stamp the two firmwares do, computed in `app/build.gradle.kts` the way `Scripts/GenVersion.sh` computes theirs, emitted as a **string resource** and shown at the top of Application Settings. Not `buildConfigField`, and that is load-bearing: a BuildConfig `String` is a compile-time constant, so the compiler inlines it into the reader and Kotlin's incremental compilation will not recompile that reader when the generated constant changes. The first cut shipped an APK containing *both* the current stamp (beside `BuildConfig`) and a three-hour-old one (beside `AppSettingsScreen`), and drew the stale copy — unfixable by reinstalling, which is what made it look like a deployment fault. A resource is read from `resources.arsc` at runtime and cannot be inlined. The firmwares never hit this because `version.h` is a real prerequisite of `Communication.o`, which forces the recompile. Before this the app was the only one of the three that could not identify its own build — and the one changing most often. The shared format is the point: the three versions a user reads off three screens are directly comparable, which is what makes "which of these is behind?" answerable at a launch site rather than from a laptop.
- **Communication screen** ([ADR-0029](adr/0029-locator-search-candidate-channels.md)): one place for everything about which channel you are on — both scans plus the receiver and locator channel fields, grouped by the user's question rather than by which device performs the work. Receiver Settings keeps name and firmware version; Locator Settings is flight configuration only. Receiver name and channel ride in one wire message but are now edited on two screens, so each screen sends the whole struct built from the last read-back and changes only its own field — otherwise a rename silently reverts a channel change. A **Find my locator** button appears on the status panel whenever the receiver is up and no locator is heard, because that is where the problem is noticed and the channel readings cannot lead you there: a receiver on the wrong channel reports that channel as perfectly clean.
- "Find a clean channel": ranks the receiver's band survey, never offers a channel with a locator decoded on it, names the occupant where the sweep reported one, and hands the choice to the ADR-0011 change flow so the locator moves and the receiver follows.
- "Find a locator" ([ADR-0029](adr/0029-locator-search-candidate-channels.md)): for one receiver and several rockets, when you power one up and cannot remember its channel. **Both scans are refused once the connected locator is armed, and that refusal does not time out** — the system locks in on an armed rocket until it is disarmed or the receiver is power-cycled. A rocket that armed on your channel and went quiet is a *range* problem, not a channel one: it is still where you left it, a band sweep cannot find it, and the 90 s of deafness would be spent not hearing it come back (decided 2026-08-30). Searches each locator's last-heard channel (remembered in `KnownLocator.last_channel`), the last attempted move, channel 0 and the current channel — four to six dwells, seconds — then offers the whole band (up to ~90 s, less where channels answer) only if that misses. A hit applies a **receiver-only** move on the tap, the mirror image of a survey pick: the locator is already there, so moving it is the one action guaranteed to lose it again. Choosing from a scan result acts; typing a channel by hand still waits for Update. Names and ids come straight off the air and are **not** password-checked; recognition happens as usual once the receiver is pointed at the channel. The occupant hint beside the channel fields obeys the same two limits: a hit the run flags as a probable near-field artifact is not treated as an occupant, and a frame that carried no id is reported as *an unrecognized locator* rather than by a hex id no locator answers to.
- Rocket location relative to the phone (map + heads-up "point at the sky" view).
- **Offline satellite maps** ([ADR-0014](adr/0014-maplibre-offline-satellite-maps.md)): pre-download a launch site's imagery (pick the area on a map or from a user-editable preset-sites CSV, choose the detail level, see a live size estimate) so the map works during recovery with no cell signal. A download runs process-wide rather than per-screen, so it survives leaving the screen and can be canceled and resumed; the region list reports each region's real completion state rather than merely that it was started. Provider licensing is unresolved for release — see the ADR.
- Spoken status callouts (TTS) so the user can keep eyes on the rocket.
- Locator and receiver configuration, including two LoRa-channel controls with distinct purposes ([ADR-0011](adr/0011-locator-lora-channel-from-app.md)): *Locator Settings → channel* moves a locator to a new channel (the receiver auto-follows), while *Receiver Settings → channel* retargets the receiver to a different locator already on another channel. An unconfirmed locator channel change is resolved by **looking before acting** ([ADR-0011](adr/0011-locator-lora-channel-from-app.md) amendment, 2026-08-30): silence does not distinguish "the locator missed the command" from "it moved and the confirmation was late", so the app runs a two-channel census search — new channel then old — and reverts the receiver only when the locator is actually heard on the old one. Heard on neither, it reports the failure and stays on the new channel, because reverting is the only action that can strand a locator whose move is flash-persistent.
- Archived-flight download, graphical flight profiles, and path export.
- **App flight logs** ([ADR-0030](adr/0030-app-flight-log.md), 2026-08-31): a per-flight CSV of what the *phone* saw, recorded automatically from 2 s before launch detection, listed on its own screen with view / share / delete. Deliberately not a second copy of the telemetry — it is the received frame **plus** the receiver's RSSI/SNR/noise-floor/bad-frame reading of it ([ADR-0019](adr/0019-channel-interference-detection.md)) **plus** what the app decided and spoke, on one timeline. None of those three survive the flight anywhere else: the link measurements are taken on the phone's side of the radio so the locator cannot know them, and the callouts left no trace once the words had gone past. **Only a launch creates a file** — pre-launch records sit in a 2 s in-memory ring, so a session of connecting, arming and surveying that never flies leaves nothing on disk. **Landing does not close it**: the recovery walk-in is when link quality matters most and is exactly the window nobody can watch, so the file runs to the disarm, a receiver/locator change, the app stopping, or the next launch. A dropped BLE link is explicitly *not* a close — the connected-locator id goes null on a disconnect as well as on a deliberate switch (see the ADR-0011 row below), and ending the file on a dropout would discard the evidence of the thing being investigated. Export is the **Android share sheet** — Bluetooth to a paired laptop, Quick Share, Drive, or save-a-copy into Downloads for a USB-C pull — chosen over a serial/SPP protocol because both of those oblige us to ship software for every PC a log is ever read on. **The 1 Hz wire rate is load-bearing here** and is why there is nothing to downsample. The ~5 Hz claim it replaces had propagated to **six comments across both apps** — `repeatsFix` and `startsNewFlight` plus their tests on Android, and the ported `TrackRecording.repeatsFix` and its test on iOS — all corrected immediately afterwards. Neither correction changes behaviour: the de-duplicator is kept, on the honest ground that it defends against *the same payload handled more than once* (the leaked-collector shape of `c8e6dc3`, which is what actually produced the 5× duplication), and the widened grounded→airborne launch trigger is kept and turns out to matter **more** at 1 Hz than its own comment claimed, since a short boost puts only a frame or two in `Launched`. All nineteen `speak()` call sites now route through one `Announcer` facade, which logs only what actually reached the speech engine.
- Remote deployment-charge testing.
- Connection authorization: password challenge on first contact with an unknown locator, a remembered store of authorized locators, and a conflicting-traffic warning (FR-P14).
- Resilient BLE link: the connection to the receiver stays up through long stretches of locator silence (locator off / on the pad / out of range), verified by probing the receiver rather than assuming silence means a dead link ([ADR-0012](adr/0012-app-ble-connection-health-probe.md)).

### 4.4 Platform parity (Android ⇄ iOS)

A native Swift/SwiftUI iOS app is under way as a **second codebase** ([ADR-0016](adr/0016-ios-port-corebluetooth-and-platform-parity.md)). All three steps of its build order are now done: the protocol + auth layer in pure Swift, the CoreBluetooth transport, and the UI. As of **2026-08-21** the app has a working flight map with the full camera model, Application Settings, Receiver Settings, Locator Settings, Flight Profiles, Download maps and Deployment Test — **every screen the Android app has**. The last three brought the archived-flight download path and the offline-map path with them; what remains on iOS is features inside screens (flight TTS callouts, the camera passthrough, the archived-path map control, path export) and hardware time. Everything testable has been exercised on hardware **except an actual flight and a real record download**; Flight Profiles has so far only been driven on the simulator against fixture data. The ADR-0006 recognition gate is complete and hardware-confirmed, including the corrected "authorization is a set, connection is one held element" model and the password challenge. **Android remains the reference implementation** — new behavior lands there first, then iOS, and never without being written down in an ADR or here first.

ADR-0016's UI/UX bar was clarified twice during that work (2026-08-19 and 2026-08-20): mirror Android's functionality **and** its UI, and depart only where Android's approach genuinely does not work on iOS. The departures that exist are recorded in `steam-pigeon-ios/docs/UI_PARITY.md` with what would close each; an unrecorded difference is a defect. **Five remain**: two of the original seven closed on 2026-08-21 because Android moved — the two unconfirmable settings (ADR-0028) and the storing of a name for every accepted locator, not only password-held ones.

**iOS has caught up with the 2026-08-21 Android session in full** (2026-08-23): the download estimate, the chart gutter, the ADR-0028 reserved fields, and the one asymmetry left in the locator-naming rule — Android remembers the name of an authorized locator it declines to connect to, and iOS now does the same on its conflict path. Two of those were confirmed on hardware 2026-08-24; the chart is deliberately held for a real flight. This is also the first cycle where behaviour flowed **both** ways to plan: two iOS-first behaviours were written as descriptions here, implemented on Android from those descriptions, and closed as divergences — the standing rule is still Android-first, and both were asked for.

The wire format is already defined twice by hand (C++ structs, Kotlin offsets); Swift makes it three, which is why parity is a stated policy. The guard is a **test triad** pinned to identical constants — firmware `static_assert`s in `MessageProtocol.hpp`, `WireLayoutTest.kt`, and `WireLayoutTests.swift` — all updated in the **same session** with cross-referenced commits. Behavioral invariants live in ADRs, not in one app's code comments, so a fix updates the ADR once and both apps follow. See [ADR-0016](adr/0016-ios-port-corebluetooth-and-platform-parity.md) for the per-layer mechanisms and the change checklist.

## 5. Operational Notes

- **Real-time budget is hard, not soft.** Every code path must complete within the 50 ms window; the design target is ~25 ms. Watch `process_dur_us` as features are added — **live only**, via `CycleProfiler` and the console `t` per-cycle breakdown. It stopped being archived per sample in `ARCHIVE_VERSION` 6 ([#38](https://github.com/fschroer/steam-pigeon-locator/issues/38)); those bytes now carry raw GPS velocity and accuracy.
- **The shared SPI2 bus is a known hazard.** Baro + IMU + flash share it. The ISR-enqueue / main-loop-drain rule in `SpiBus` exists specifically because a violation caused a false apogee and premature deployment. Any new SPI user must obey it — including the **flash**: the UART2 console and LoRa-RX paths were later found doing flash I/O in ISR context (corrupting concurrent IMU/baro reads) and moved to main-loop context ([ADR-0010](adr/0010-archive-flash-robustness.md)). Never touch the flash from an ISR.
- **Software baro filtering is mandatory.** The MS5611 has no hardware spike rejection; spurious values must be filtered in software, and D1/D2 conversion sequencing must keep a valid pressure available every window.
- **Raw vs. fused is a policy, not an implementation detail.** The requirements mandate raw baro/GPS for Priorities 1–2 (and the high-rate gyro strapdown for the Priority-3 air-start gate) over unvetted fusion. As of PR #9 (2026-06-18) the deployment path is fully on raw baro — apogee, main-deploy altitude, and deployment velocity all flow through `SelectDeploymentSource()` — and the EKF is being retired from the real-time path (ADR-0005). Treat the raw-vs-fused boundary as a deliberate, tracked policy, not something to "fix" ad hoc.
- **The wire format is defined in two places.** `MessageProtocol.hpp` (C++ packed structs) and the Kotlin side (`RocketState.kt` + `FlightDataRepository.kt` manual byte offsets) must be hand-synchronized. There is no shared schema or generator. This is the highest-probability source of future "conflicting patches."
- **Arming triggers re-calibration.** Mounting detection and EKF re-init happen on each arm; arming the rocket in a non-final orientation and then re-orienting it will invalidate the calibration.
- **Flights are capped at 8 minutes** of recorded data; the state machine force-closes to `Landed` at that limit (measured on the GPS-disciplined flight clock) so timestamps never exceed the recorded span. On a *normal* landing the record deliberately continues for a **~2 s post-landing tail** (~40 samples logged in the `Landed` state) before closing, so the recorded span extends ~2 s past the `LandingTimestampMs` event and captures the settled-on-ground signal ([ADR-0007](adr/0007-prelaunch-ring-monotonic-clock.md) 2026-07-15 amendment). The force-close path arms no tail.
- **Archived time is real time; the record starts at launch ONSET (t≈0 at launch).** Timestamps come from a GPS-PPS-disciplined monotonic clock, not a per-cycle counter ([ADR-0007](adr/0007-prelaunch-ring-monotonic-clock.md)). **Updated 2026-07-15 (ADR-0007 amendment):** the epoch is now anchored to thrust onset (`AnchorRecordToLaunchOnset`), so `time_ms = 0` ≈ launch and the pre-onset pad data is dropped — *superseding* the earlier "record leads launch by ~2 s / launch at ~2000 ms" behavior. Keeping both launch-at-0 and the pre-launch lead-in would need a signed timestamp (deferred). `FlightSample` layout unchanged → `ARCHIVE_VERSION` stays 5 (only `timestamp_ms` semantics change).
- **`FlightSample` is size-locked at 88 bytes and the archive holds 9 records.** The binding constraint is **samples per 512 B chunk**, not bytes: `512/sizeof` is integer division, so cost rises in steps. Measured against this geometry (8 min/record, 20 Hz, 4 KB sectors, 8,323,072 B archive region): **≤ 82 B → 6/chunk → 10 records; ≤ 90 B → 5/chunk → 9 records; ≤ 102 B → 8 records; ≤ 110 B → 7 records.** At 88 B a record is 892,928 B and nine fit in 8,036,352 B. `ArchiveTypes.hpp` carries this table; `record_count` in `Archive.hpp` and `kRecordCount` in `Tests/ArchiveRoundTrip` must move together, and the test now fails fast with a named message if they drift. `FlightSample` has **5 reserved bytes**, which are free headroom only up to 90 B — the field after that costs a record.

  **`ARCHIVE_VERSION` 6 ([#38](https://github.com/fschroer/steam-pigeon-locator/issues/38)) is a full break, not an additive change.** Earlier growth reused space that already read back as zero (`_pad[1]` → `gps_fix_sv`), so the version held at 5. v6 changes the *meaning* of bytes holding real data and drops a record, so old records cannot be interpreted at all: `ValidateHeaderForConfig()` rejects them and the data menu will not list them. **Download anything you want before flashing.** What changed:
  - the four per-cycle timing fields → raw GPS velocity (`gps_vel_{n,e,d}_cms`) + `gps_h_acc_cm`;
  - `lat_rad`/`lon_rad` doubles → `lat_1e7`/`lon_1e7` int32 in the receiver's native degrees × 1e-7 (−8 B, and *more* precise at 1.11 cm);
  - bit-packed status → one byte each: `flight_state`, `armed`, `ekf_health`, `gps_fix_type`, `gps_num_sv`, plus `accel_source` and `pps_status`;
  - the **non-selected** accel channel (`accel_alt_cg[3]`, 0.01 g/LSB) — ADR-0004 names its absence as a vetting gap, since a scale mismatch between channels biases every accel-driven state and was invisible in every flight recorded so far.

  **This also changes a LoRa message.** `FlightMetadata` carries one `FlightMetadataRecord` per archive slot, so 10 → 9 records shrinks it 106 → 96 B (app payload 100 → 90). The Android app's `Protocol.*` constants and `WireLayoutTest.kt` need the matching change or the flight list will misparse.

- **GPS receiver configuration is owned for the whole flight, not just boot** ([ADR-0017](adr/0017-gps-receiver-configuration-ownership.md)). Under ADR-0005 raw GPS is the *only* position source, so a fix that stops tracking is an outright Priority-2 (FR-P2) failure. Two distinct modes were observed in flight and both are now handled: the receiver losing its RAM-layer configuration and never regaining it (a 3 s stale-fix watchdog re-asserts the whole block, un-ACKed — an ACK wait would overrun the 50 ms budget), and the factory-default *Portable* dynamic model invalidating the solution above its 50 m/s vertical limit for an entire ascent (`CFG-NAVSPG-DYNMODEL` is now scheduled by flight phase: AIR4 → PORT at main → PED when landed). Receiver configuration must stay re-assertable in flight; never assume a boot-time `CFG-VALSET` still holds.
- **A CubeMX/linker regeneration can silently break the fault log.** The persistent `FaultRecord` lives in a hand-added `.noinit` section in `STM32WL5MOCHX_FLASH.ld`; if that section is lost, crash/hang diagnostics stop surviving reset (NFR-10, [ADR-0008](adr/0008-watchdog-fault-log.md)). The IWDG timeout must also stay above the worst-case cycle time so a slow-but-valid cycle can't false-trip a reset.
- **A CubeMX regeneration can also silently revert two ADC settings the battery reading depends on.** `MX_ADC_Init` must keep `TriggerFrequencyMode = ADC_TRIGGER_FREQ_LOW` (the battery read enables the ADC, converts once and disables it again roughly once per second, exceeding the datasheet `tIdle` between triggers — CubeMX's default is `HIGH`), and must keep the `HAL_ADCEx_Calibration_Start` call in `USER CODE BEGIN ADC_Init 2` (without it `CALFACT` stays 0 and every conversion carries the die's raw offset — measured at ~83 counts / ~67 mV on one board, 2026-08-08). `ADC.TriggerFrequencyMode` was added to `Locator.ioc`'s `IPParameters` so the first survives regeneration — **verified 2026-08-08** by setting the line to `HIGH` by hand and regenerating (CubeIDE 1.19.0): CubeMX wrote `LOW` back, and the `USER CODE ADC_Init 2` block carrying the calibration call survived the rewrite intact. Note CubeMX only rewrites `adc.c` when its model differs from the file, so a regeneration that leaves it untouched means the setting is already right, not that it was skipped. Symptom of the calibration loss: a grounded BATTLVL node reading tens of millivolts and a VREFINT-derived VDDA reading low. Both are visible in the `v` console diagnostic ([bench-battery-diag.md](bench-battery-diag.md)).
- **The external flash needs a reset it can't get from an MCU reset.** A debugger/flash or watchdog reset restarts the MCU but not the SPI flash, which can be left unreadable until a power cycle; the firmware issues a software reset at boot to restore it ([ADR-0010](adr/0010-archive-flash-robustness.md)). If archived data ever "disappears" after flashing but returns after a power cycle, that reset (or the `CSB_MEM` pull-up) is the thing to check — the data is not lost.
- **Changing the record structure requires erasing the archive.** The record geometry is derived from `sizeof(FlightSample)` and the stat set; a layout change makes old records unreadable and their headers stale at shifted offsets. Export any wanted flights first, then use the data-menu full erase (`e`) to reset the archive region ([ADR-0010](adr/0010-archive-flash-robustness.md)). This is also why `ARCHIVE_VERSION` must be bumped on any layout change.
- **One charge fires at a time.** Overlapping deployment commands are queued, not fired simultaneously — relevant when reasoning about current draw and near-simultaneous primary/backup events.
- **Never change the receiver's RF frequency mid-transmit.** When the receiver follows a locator channel change ([ADR-0011](adr/0011-locator-lora-channel-from-app.md)), the `SetChannel` must be deferred until the forwarded command has finished transmitting (after `OnRadioTxDone`) — `radio_->Send()` only *starts* the TX. Switching between `Send()` and TxDone corrupts the forward, so the locator never moves while the receiver does (a bench-observed failure). The locator↔receiver channel pair must stay in sync; the app's confirm/recovery logic is the safety net if it drifts.
- **On the app, GATT silence is not a dead link.** The BLE health watchdog must not tear down the receiver connection just because no data has arrived — a healthy receiver relays nothing while the locator is quiet. It probes the receiver (`ReceiverInfoRequest`, which the receiver answers itself) and only reconnects after repeated unanswered probes ([ADR-0012](adr/0012-app-ble-connection-health-probe.md)). Reverting to tear-down-on-silence reintroduces the disconnect/reconnect loop. This depends on the receiver answering receiver-info requests unconditionally (FR-R2) — do not gate those replies behind locator activity.

## Appendix A — Open Issues & Inconsistencies

These are points where the requirements outline, the firmware, and the app disagree, or where the requirements are ambiguous enough to invite divergent implementations. Ordered roughly by impact on the stated priorities. None of these are edits to the code or the requirements — they are flagged for an explicit decision.

> **Appendix item → GitHub issue** (numbers differ because the issues were filed in a different order): 1 → [#1](https://github.com/fschroer/steam-pigeon-locator/issues/1) · 2 → [#2](https://github.com/fschroer/steam-pigeon-locator/issues/2) · 3 → [#8](https://github.com/fschroer/steam-pigeon-locator/issues/8) · 4 → [#3](https://github.com/fschroer/steam-pigeon-locator/issues/3) · 5 → [#4](https://github.com/fschroer/steam-pigeon-locator/issues/4) · 6 → [#5](https://github.com/fschroer/steam-pigeon-locator/issues/5) · 7 → [#6](https://github.com/fschroer/steam-pigeon-locator/issues/6) · 8 → [#7](https://github.com/fschroer/steam-pigeon-locator/issues/7). See the **Open Issues Tracker** near the top for milestone grouping.

**1. Main-chute altitude trigger uses fused AGL, contradicting the Priority-1 "raw baro" policy. (High impact.)** → [#1](https://github.com/fschroer/steam-pigeon-locator/issues/1) — **Resolved 2026-06-18** (PR #9, ADR-0003): main primary/backup now gate on raw-baro-derived AGL via `SelectDeploymentSource()`; #1 closed.
`FlightManager::UpdateFlightState()` fires main primary/backup on `nav_solution.altitude_agl_m` — the **EKF-fused** AGL — while the requirements mandate raw baro for deployment-critical altitude until fusion is vetted. This is especially notable because the apogee detector right above it was *deliberately* switched to raw baro after the 2026-06-14 flight, where the same EKF's vertical channel diverged. The most safety-critical altitude decision in the system currently trusts the output the apogee logic stopped trusting. *Decision needed:* either move main-deploy altitude to raw baro AGL for consistency with the policy, or formally declare fused AGL "vetted" for this use and update the requirements to match.

**2. Physical-deployment sensing and main-velocity logic use fused vertical speed. (Medium impact.)** → [#2](https://github.com/fschroer/steam-pigeon-locator/issues/2) — **Resolved 2026-06-18** (PR #9, ADR-0003): `pre_main_velocity_` and the physical drogue/main thresholds now use raw-baro-derived velocity; #2 closed.
`pre_main_velocity_`, physical drogue/main detection, and the main-deploy velocity checks all read `nav_solution.vertical_speed_mps`. Physical-deployment sensing is Priority 11 (general interest), so this is lower stakes than Item 1 — but it relies on the very fused-velocity signal the apogee detector abandoned as unreliable. *Decision needed:* confirm whether fused velocity is trustworthy here, or fall back to a raw-baro-derived velocity.

**3. "Velocity must come from a proven source" is undefined. (Policy gap.)** → [#8](https://github.com/fschroer/steam-pigeon-locator/issues/8) — **Resolved** (ADR-0003): the canonical Priority-1 velocity source is raw-baro-derived velocity, used uniformly by apogee, main, and physical sensing via `SelectDeploymentSource()`; #8 closed (`in-doc`).
The requirements require a "proven source" for velocity but never name one. Today, apogee uses raw-baro-derived velocity while main/physical logic uses fused velocity — two different "sources" for nominally the same quantity. *Decision needed:* designate the canonical velocity source(s) per flight phase so future code doesn't pick arbitrarily.

**4. Requirements say the GPS shares the SPI bus; it is actually on I2C. (Documentation error.)** → [#3](https://github.com/fschroer/steam-pigeon-locator/issues/3) — **Resolved 2026-06-16:** requirements outline corrected to "baro, IMU, and external flash share SPI; GPS on a separate I2C bus."
The requirements state "the barometric pressure sensor, IMU, and GPS share a common SPI bus." In the firmware, `SAMM10Q` is an I2C device (addr 0x42, `hi2c2`), and `SpiBus` documents SPI2 as shared by baro + IMU + **flash**. The real contention to "avoid conflicting traffic" on is baro/IMU/flash, not the GPS. *Decision needed:* correct the requirements text to name the flash (and the actual buses), so the bus-contention requirement points at the right hazard.

**5. Two hand-synchronized definitions of the wire protocol. (Architectural risk.)** → [#4](https://github.com/fschroer/steam-pigeon-locator/issues/4) — **Addressed 2026-06-16** with a layout cross-check (decision: cross-check over codegen): firmware `static_assert`s on every message struct's `sizeof` (`MessageProtocol.hpp`, `FlightProfileCodec.hpp`) + app `WireLayoutTest.kt` asserting the matching constants. Catches size drift; a same-size field reorder would still need offsetof asserts.
The packet structs in `MessageProtocol.hpp` and the manual offsets/sizes in the Kotlin app must be kept byte-identical by hand (the Kotlin source even carries "must stay in sync with MessageProtocol.hpp" comments). There is no single source of truth. *Recommendation:* generate both sides from one schema, or at minimum add a cross-checked layout test. This is the most likely origin of silent, hard-to-debug field-misalignment bugs.

**6. Enum drift between firmware and app. (Low impact, but a sync hazard.)** → [#5](https://github.com/fschroer/steam-pigeon-locator/issues/5)
The app's `FlightStates` adds a client-only `NoSignal(9)` and renames states (`WaitingForLaunch` vs firmware `WaitingLaunch`; `DroguePrimaryDeployed` vs firmware `DroguePrimaryEvent`). The wire values (0–8) match, so it works today, but the naming implies different semantics — the firmware "Event" is *charge fired*, whereas the app "Deployed" reads as *physically deployed*, which the firmware tracks separately. *Recommendation:* align names or document the mapping in one place.

**7. The requirements outline has no IDs, versioning, or acceptance criteria. (Process gap.)** → [#6](https://github.com/fschroer/steam-pigeon-locator/issues/6) — **Resolved 2026-06-16:** restructured to [SteamPigeonRequirements.md](SteamPigeonRequirements.md) v2.0 with `FR-`/`NFR-`/`HW-` IDs, a functional/non-functional split, the vetted-fusion gate (NFR-2), a glossary, and a change log.
For a document meant to "drive consistently to a goal," the outline would benefit from: numbered/traceable requirement IDs; a split between functional and non-functional ("other notes" mixes hard real-time constraints in with a bus-wiring claim); explicit acceptance criteria for the "vetted fusion" gate that governs Priority 1–2; and a glossary (noseover, AGL, ZUPT, primary/backup roles). Without the "vetted" gate being defined, Items 1–3 cannot ever be closed objectively.

**8. Residual/legacy definitions worth auditing. (Cleanup.)** → [#7](https://github.com/fschroer/steam-pigeon-locator/issues/7) — **Resolved 2026-06-16:** `MsgState` (unused) and the reset-but-unread `burnout_detected_` / `drogue_deployed_` / `main_deployed_` flags removed.
`MessageProtocol.hpp` carries both `MsgState` and `MsgType`; `MsgState` appears unused by the live path. `FlightManager` keeps several state flags (`burnout_detected_`, `drogue_deployed_`, `main_deployed_`) that are reset but not read. Not bugs, but they invite confusion during future edits. *Recommendation:* confirm and remove if dead.
