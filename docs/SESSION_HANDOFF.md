## 2026-08-18 session — iOS CoreBluetooth transport works on hardware; a stale receiver exposed an app-visible wire-format skew — COMMITTED + PUSHED, HARDWARE-CONFIRMED

App and firmware-flashing only; **no firmware source changed**. Steps 1–2 of the [ADR-0016](adr/0016-ios-port-corebluetooth-and-platform-parity.md) build order are done, and the iOS app has now talked to a real receiver.

### A. ⚠️ ANDROID ACTION: the receiver-info poll is rejected against pre-`aee36fe` receivers, and it fails invisibly

**Read this before diagnosing anything about noise floor or interference classification.** A receiver flashed before receiver `aee36fe` (2026-08-11, "report channel status in ReceiverInfo") sends the **27-byte** `ReceiverInfoMessage` — `PacketHeader 6 + lora_channel 1 + device_name 20`, with no `noise_floor`, no `bad_frames`, and no `static_assert`. Both apps expect the 30-byte form (`RECEIVER_INFO_PAYLOAD_SIZE = 24`), frame 27 real bytes plus 3 taken from whatever follows, and fail the CRC. **Every receiver-info reply is silently discarded.**

**It is invisible on both platforms, by design.** [ADR-0012](adr/0012-app-ble-connection-health-probe.md) records liveness for *every inbound byte before framing* — deliberately, so a corrupt reply still proves the link carries traffic. So the health watchdog reports a perfectly healthy link while the message it depends on never parses. What is actually lost is the **channel-status noise floor**, which [ADR-0019](adr/0019-channel-interference-detection.md) exists to deliver during locator silence: it is the only floor reading that reaches the app without a locator broadcast to ride on. An app fed no floor at all is not obviously distinguishable from one fed a quiet floor.

Confirmed fixed by reflashing the receiver: 30-byte frames, zero CRC errors. **Android has not been checked against a stale receiver and should be**, since the symptom there is "interference classification looks off" rather than anything pointing at framing.

**The general lesson, worth more than this instance:** an app-side CRC gate turns a wire-format version skew into silence, not into an error. The three-way `static_assert`/`WireLayoutTest`/`WireLayoutTests` triad pins the three *source trees* against each other; it says nothing about the firmware actually flashed on the bench hardware. Nothing in the system reports a device's wire-format version, so a stale device degrades quietly.

### B. iOS transport (iOS `7139825`, `c854114`) — scan, connect, notify, and the ADR-0012 watchdog, all confirmed on hardware

Service-UUID scanning on `FFE0`, `FFE1`/`FFE2` as on Android, MTU re-queried per write and never cached, State Preservation & Restoration, transport identity `peripheral.identifier` (locator identity still keys on `locator_id`, so [ADR-0006](adr/0006-locator-connect-password.md) ports unchanged). Confirmed against a real receiver: connects, `preLaunchData`/`telemetryData` at 1 Hz, and — the case that mattered — **the link stays up through arbitrary locator silence on probe replies alone**, which is the loop ADR-0012 was written to end.

The ADR-0012 watchdog is deliberately **pure logic with no CoreBluetooth in it**, so its invariants are testable on a Mac. One test runs 200 idle probe/answer cycles and asserts the link is never condemned. Reintroducing the original tear-down-on-silence bug fails the suite.

`OutboundMessage` enforces [ADR-0020](adr/0020-targeted-locator-commands.md) in the type system: a locator-directed command **cannot be constructed** without a target, and target `0` is refused because it addresses nothing.

**Deployment note:** background BLE needs no paid Apple membership — verified on the signed device build, whose only entitlements are `application-identifier`, `team-identifier`, `get-task-allow`. `bluetooth-central` is an Info.plist key, not an entitlement. Also: `INFOPLIST_KEY_UIBackgroundModes` is **accepted as a build setting and then silently dropped** — Xcode promotes only an allowlist, and that key is not on it. It lives in a partial `Config/Info.plist`, which must sit **outside** the file-system-synchronized group or it is also copied as a resource and the build fails with "Multiple commands produce".

### C. How the skew was found — diagnostics over inference, again

Four hypotheses, **the first three wrong**, each killed by a measurement rather than an argument:

| # | Hypothesis | Killed by |
|---|---|---|
| 1 | The relayed `Startup` message (74 B, unframed) pollutes the count | 3000 simulated serials: 0 bad frames 99.9% of the time |
| 2 | Contention when locator traffic starts | bad frames appeared with the locator **off** |
| 3 | One stale field (`noise_floor`) | single-byte brute force found no fix |
| 4 | **Older, shorter message** | sender's CRC verifies at exactly 27 bytes |

The app now reports, per rejected frame: both CRCs, the length at which the sender's CRC *does* verify, the single-byte fix if one exists, embedded header positions (truncation signature), and a diff against the previous reject. The ±2 length scan was itself a bug — a 3-byte difference was out of range, which is why this looked like corruption for two rounds. It scans every prefix now.

**Reading the firmware did not solve this and twice pointed the wrong way.** `ComputeMessageCrc<TMsg>` hashes the whole struct, so the receiver's CRC *should* have moved when `noise_floor` moved; that it did not was the clue, and it was only legible once the app reported the sender's CRC alongside its own.

## 2026-08-06 session — interference detection (ADR-0019) and command addressing (ADR-0020) — COMMITTED + PUSHED, BENCH-VALIDATED

Two lines of work, one asked for and one found while testing it. **[#32](https://github.com/fschroer/steam-pigeon-locator/issues/32) and [#34](https://github.com/fschroer/steam-pigeon-locator/issues/34) are closed and bench-validated; [#33](https://github.com/fschroer/steam-pigeon-locator/issues/33) is open** with three of four criteria confirmed.

### A. Locator commands were unaddressed broadcasts — the safety fix ([ADR-0020](adr/0020-targeted-locator-commands.md), [#34](https://github.com/fschroer/steam-pigeon-locator/issues/34))

**Read this first if you touch the command path.** A channel change sent to one locator moved **both** locators powered on that channel. No app→locator command carried a target; the receiver relays over LoRa, which is a broadcast medium, and every locator in an accepting state obeyed.

The channel was the least of it. `LocatorCfgChgRequest` carries the whole `RocketPersistentSettings`, so a bystander received the target's **deployment channel modes, drogue delays, main deploy altitudes and device name** — pyro configuration rewritten on a rocket the user never connected to. And `ArmRequest` was in the same class: **on a shared launch channel, pressing Arm armed every disarmed locator on it.**

This was the gap in [ADR-0006](adr/0006-locator-connect-password.md), not a new defect. That ADR claims to prevent "accidental cross-connection among many users at a launch", but its gate only governs whose telemetry the app *acts on* — Decision 5 says the locator keeps accepting well-formed commands. The soft/hard-gate axis does not apply either: this is an *honest* app doing exactly what its user asked, reaching rockets it never meant to address. No app-side gating fixes a wire format with no addressee.

Eight commands now carry `uint32_t target_locator_id` after the header; the locator discards anything not matching its UID **before any state change**, and `0` matches nothing so an older app fails closed. Locator `043ec52` + receiver `453e892` + app `dcaf709` are three halves of one change and **must be flashed together** — but unlike previous breaks this one fails *safe*. `39ece0f` then made the check unconditional and deleted the allowlist: every frame reaching the locator is an app command, so requiring an address from everything means a new command is protected by default and forgetting costs "does nothing" instead of "reaches every rocket".

**Two things found on the way.** `sendFlightDataAck` built its own frame instead of going through `sendMessage`, so it had *neither* the connection gate nor addressing. And addressing commands did **not** make derived state safe: with only one locator arming, the app still flipped armed/disarmed because `computeExpectedPacketLength` derived armed state from the message *type*, in the framing path, before anything knew whose packet it was (app `ad70d93`). The rule, now in ADR-0020: **once commands are addressed every *response* is implicitly addressed too, but unsolicited broadcasts arrive from everyone, so anything derived from them must be gated on `locator_id`.**

### B. Interference detection ([ADR-0019](adr/0019-channel-interference-detection.md), [#32](https://github.com/fschroer/steam-pigeon-locator/issues/32) closed, [#33](https://github.com/fschroer/steam-pigeon-locator/issues/33) open)

Tiers 1–2 report SNR (already measured and discarded — a dead store in `OnRadioRxDone`) plus an idle-channel noise floor, classified app-side so thresholds tune without reflashing. Tier 3 is an on-demand channel survey, **two-phase**: a strided coarse pass shortlists five candidates, each then given a full broadcast period of dwell, because a 12 ms dwell misses a 14 %-duty 1 Hz emitter ~86 % of the time — a sweep once ranked the channel both locators were sitting on as the quietest in the band.

**The ADR's framing was too narrow and its final section says so.** Everything in the Decision is about measuring *power*, which is right for a non-locator emitter and close to useless for another locator on the channel. **LoRa capture is strong: co-channel interference displaces rather than corrupts.** The receiver locks the first preamble and decodes that packet cleanly; ours is never heard. Nothing fails a CRC, SNR is pristine, the floor often stays quiet. Four bench rounds were spent adding measurements that could not fire. The decisive signal was in hand throughout — **the app receives and identifies the interfering locator on every one of its broadcasts**, because each carries a cleartext `locator_id`. A foreign id now counts as occupancy directly (app `4e3732f`).

**The failure mode that recurred four times, and the test that finds it.** Each was a mechanism disabled by exactly the condition it existed to detect: the noise floor sampled only inside the post-broadcast window (which never reopens under loss); "elevated" judged against a session baseline (which absorbs interference present at startup); a 12 ms survey dwell (versus the 1 Hz emitter it hunted); and the verdict computed only on packet arrival (versus a dropout, which is the absence of arrivals). **Assume the condition is fully present, then check the detector still runs.** ADR-0019 carries the table.

**Also worth not rediscovering.** A sentinel is a wire constant: `kNoiseFloorUnknown` is `INT16_MIN` in an `int16_t` and arrives as −32768, not `Int.MIN_VALUE` — the comparison never matched, the baseline latched onto it, and every reading looked ~32000 dB elevated. `static_assert` and `WireLayoutTest` pinned every struct *size* and no *value*; sentinels are pinned now. And `IsChannelFree()` is unusable in the periodic path — it switches the modem to FSK and leaves the radio in standby.

**Diagnostics beat inference here, decisively.** Three consecutive rounds were diagnosed by reasoning from a symptom and two were wrong, including one where the fix went into a `Debug` build while the hardware ran `Release` — **build `Release`, that is what gets flashed.** The `[survey]` console traces and the bad-frame counter each ended a loop in one test. Both are documented in the user manual, Appendix D.

**Confirmed on hardware:** interference detection fires correctly for two locators sharing a channel, armed or disarmed; the survey completes, restores its channel and refuses while armed; near-field saturation is reported distinctly from real per-channel traffic. **Not confirmed:** anything at genuine range. Every result this session comes from two locators a few feet apart, where near-field bleed dominates and the numbers look nothing like a flight. Thresholds are reasoned from the link budget, not fitted — all app-side, so tuning needs no reflash.

Payload length does not move the link budget at all — sensitivity is set by SF/BW/CR.
- **Screen stays on** while the app is in the foreground (`FLAG_KEEP_SCREEN_ON`, window-scoped).
- **Dark theme** regardless of the system setting.

**NOT YET CONFIRMED — the whole rest of this session is untested in flight:**
- **Voice gating on a real fix.** Every spoken distance now goes through one nullable phrase, non-null only when the locator reports a good fix *and* both ends of the vector are real coordinates. The "12 million meters" callout was a launch point captured with **no GPS lock, sitting at 0,0** — the great-circle distance to null island, read out as a recovery bearing.
- **Landing callout + stale-event suppression.** The landing announcement required the rocket to already be below 30 m or 3 s from the ground *at the last packet*, so losing the link at 300 m — the normal way a descent ends — meant it never fired. It now dead-reckons the touchdown from the last altitude and descent rate (300 m at 5 m/s → ~60 s later), with a 5 s floor so a routine dropout cannot conclude a flight. Once the rocket is down, event announcements stop: a link returning post-landing used to deliver the whole flight in one burst ("main charge", "main deployed") over a rocket already in a field. Direct cause was a confirmed `Landed` state being handled *after* the per-event checks; it is handled first now.
- **New health callouts**, edge-triggered: "GPS fix lost/restored" (only while messages are arriving — with none, the last-sent `gpsStatus` is stale) and "Telemetry lost/restored" at 3 s.
- **Descent warnings** 30 → 50 m/s, minimum gap 4 → 10 s.
- **Flight-path reset** now fires on any grounded → airborne transition. **Read this before relitigating it:** the old narrow rule was *not* defeated by losing a packet or two — the locator reports `Launched` for the whole boost and any one of those packets fired the reset. It needed the entire boost window lost. The stale path actually seen in the field was the recognition gate above dropping all telemetry, so nothing ever cleared the path restored from disk at startup. This rule is hardening, not that fix. Two traps closed, both pinned by tests: `NoSignal` is `FlightStates.fromUByte`'s fallback for **any** unrecognized state byte, so counting it as grounded would erase an in-flight track; and an app restarted mid-flight must not read its first packet as a launch.

**Two defects the wire change exposed and fixed:** `requestConnectToConflict` could verify a typed password against a *different* locator's frame (latent before; reachable now that armed locators raise conflicts too), and a recognized armed locator had no name to display, since the status panel reads it from config and config rides on `PreLaunchData` only.

### B. Real-time performance — the big picture (a 6-hour rabbit hole; read this before optimizing anything)
Original `process_dur_us` looked alarming (~25–47 ms). The causes, in order of impact:
1. **This core has NO FPU.** STM32WL5MOC M4 → `-mfloat-abi=soft`, all float software-emulated (IDE offers only FPU=None). **This is hardware, not a bug — do NOT try hard-float.** It means float *op count* is the cost.
2. **Build config.** Debug = `-O0`, Release = `-O3`. The Release config was a stale stub **missing the `Rocket` source folder, the `../Rocket/*` + `Accelerometer`/`BMP280` include paths, and the C++/C language standards (gnu++17/gnu18)** — all present in Debug. Fixed in the IDE (un-exclude `Rocket`, copy includes + std). **Recommended: clone the Debug config and just set -O3** to avoid this whack-a-mole. Fly/measure on -O3.
3. **ITM trace was blocking.** `ITM_Trace::send` spun `while (ITM->PORT==0)` — blocks forever when SWO isn't drained (standalone, or a debugger without the SWO console open). Called 3×/cycle in `MS5611OCCallback` (an ISR) → stalled the ISR → inflated **every** profiled segment, and `-O3` can't speed a busy-wait. **Fixed to non-blocking (drop if port busy).** This was also a real **flight-safety bug** (ITM is enabled in Release; a debugger-less flight would stall). Keep it.
4. **EKF covariance = ~13 ms of soft-float.** Optimized to ~7.6 ms — see **[ADR-0013](adr/0013-realtime-ekf-fpuless-covariance-heuristics.md)**. **EKF kept LIVE for observation** (amends ADR-0005); `m_gps_only_` retired so it fuses through descent.

### E. Air-start tilt — what's actually wrong (don't relitigate as "gyro drift")
Flight tilt grew monotonically 4.5→123°. Key insight (issue #23): the ~250 dps axial spin **averages out** transverse gyro errors (bias/cross-axis/misalignment → bounded coning over ~1.4 s/rev), so the growth is **largely REAL rotation** (a slow low-power rocket genuinely arcs over + tumbles) plus **unbounded** open-loop drift — NOT the ~6° that simple bias would give. Bare gyro integration is unbounded + unvalidated → unusable for a safety-critical firing gate regardless of accuracy. Fielded air-start systems have a **second attitude reference**; here that's **GPS velocity-vector aiding** (nose ≈ velocity for a stable rocket). The cardinal mounting map is CORRECT (verified by integrating the archived gyro — it reproduces the recorded tilt); the gap is a bounding reference + fine calibration, not the axis mapping.

### F. Heuristics to NOT accidentally break (future context)
- **EKF covariance ([ADR-0013](adr/0013-realtime-ekf-fpuless-covariance-heuristics.md)):** `predict()` computes only the **upper triangle** of `P` (symmetric) and **copies rows/cols 9..14** (bias states = pure-identity `Φ` rows, `kDyn=9`). **If anyone gives the biases dynamics (Gauss-Markov bias, etc.), `Φ` rows 9..14 stop being identity and the copies silently produce a WRONG covariance** — revert to full loops / adjust `kDyn`. `symmetrizeP()` must stay (diagonal floor + used by the non-symmetric measurement updates). Verified numerically identical (host, ~7e-8).
- **No FPU:** optimize float *op count* (structure, not micro-ops); covariance is O(n³) in software.
- **ITM `send` must stay non-blocking.**

## Flight-profile transfer reliability — COMMITTED & BENCH-TESTED (happy path) (2026-07-04)

## Firmware state (on master, mostly UNTESTED on hardware)
- **Strapdown** (`AttitudeEstimator`): seed `quatFromAccel(−accel)` + at-rest gyro-bias learning + negated tilt-correction blend. Drives the orientation display via `getStrapdownQuat` (Y-reflected).
- **NFR-9 high-rate gyro path — IMPLEMENTED & BENCH-CONFIRMED at ~480 Hz (GPS/TIM2):** gyro batched into the ISM6HG256X FIFO at 480 Hz; `ISM6HG256X::drainFifoGyro()` reads the FIFO and `Navigation::Update()` integrates each word, decoupled from the slow path (no 480 Hz SPI ISR — respects NFR-4/NFR-5). **Additive & non-breaking:** if the FIFO is unconfigured/empty (or NAV_TEST replay), it falls back to the single output-register propagate at the loop dt.
  - **Loop rate:** `Update()` runs at the **~20 Hz** super-loop cadence (per the TIM17 tick + once-per-second radio TX; consistent with dt=1/480 ⇒ ~24 words/drain at 20 Hz). An earlier "~150 Hz" claim was a `HAL_GetTick` artifact (see below) — disregard it.
  - **dt is GPS-disciplined, NOT 1/480.** Per-sample dt = (TIM2 interval since last drain ÷ `Pps_GetTim2TicksPerSec()`) ÷ words drained, clamped to [1/4000, 1/120]; holds 1/480 until PPS lock (`m_strapdown_dt_per_word`). This anchors integration to GPS time — immune to MSI inaccuracy, the IMU oscillator (~0.16 %, measured), and **`HAL_GetTick` (see below)**. TIM2+PPS (`elapsed`, exposed via `Pps_GetTim2TicksPerSec` in main.c) is the trusted timebase.
  - **`HAL_GetTick` is RTC-based, NOT SysTick — and is a debugger trap.** `sys_app.c` overrides `HAL_InitTick` (no-op — SysTick never started), `HAL_GetTick` (→ `TIMER_IF_GetTimerValue()`, the RTC/LoRaWAN TimerServer), and `HAL_Delay`. This is the **standard ST LoRaWAN low-power timebase and is correct in production** (~ms resolution; the EKF `dt_s`, sensor timeouts, and `HAL_Delay` across `Rocket/` all rely on it and work). BUT the RTC runs in the backup domain independent of CPU halts, so **under a debugger it freezes or jumps** — which is what produced every phantom rate this session (1477 Hz, 150 Hz loop). **Do not use `HAL_GetTick` to measure anything while halted at a breakpoint; use TIM2.** Not a firmware bug — by design.
  - **Gyro ODR fixed at 480 Hz (was 60 Hz — bug).** `configureOdrAndRanges` tied the gyro `CTRL2` ODR to `sample_rate_hz` (clamped to 20 → `0b0101` = 60 Hz), starving the 480 Hz FIFO of real samples (bench showed n≈7–10/loop, not ~24). Gyro ODR is now a fixed `ODR_G_480` (`0b1000`), decoupled from the 20 Hz loop and matched 1:1 to `FIFO_BDR_GY_480`. This also fixes a latent integration-rate mismatch: `propagate()` uses `dt=1/480`, which was wrong while the gyro truly ran at 60 Hz. The low-g accel (`CTRL1`) intentionally stays at the loop-rate ODR (tilt correction is quasi-static, 20 Hz).
  - **FIFO register block confirmed against ISM6HG256X DS15034 Rev 2** (datasheet at `docs/datasheets/ism6hg256x.pdf`): `FIFO_MODE=110b`=continuous (Tbl 42), gyro `TAG_SENSOR=0x01` (Tbl 232), `DIFF_FIFO_8`=`FIFO_STATUS2` bit 0 (Tbl 81).
  - **BDR_GY must be set ABOVE the gyro ODR (`1001b`, not `1000b`).** Per Tbl 40, `1000b`=480 Hz and `1001b`=960 Hz; per Tbl 57, ODR_G=`1000b`=480 Hz. EMPIRICALLY, BDR == ODR (both 480) batched at **half** rate (GPS/TIM2: 232 Hz); BDR one notch above (`1001b`) captured every sample (~480 Hz, no duplication — ODR caps the stream). **The datasheet documents no BDR-vs-ODR rule; the cause of the BDR==ODR halving is unconfirmed.** (A prior "table offset by one" note was wrong; `1000b` genuinely *is* 480 Hz in Tbl 40.) To nail the mechanism, an isolating test is ODR=240/BDR=480. The earlier `1477 Hz`/`3×` numbers were `HAL_GetTick` artifacts, never real.
  - **Readout is per-word (1 tag + 6 data, one SPI transaction each):** the datasheet documents only a single word across `0x78–0x7E`, so a multi-word burst is *not* relied on (reading past `0x7E` walks into regular registers, not the next FIFO word). ~3 words per `Update` (480 Hz ÷ ~150 Hz) × 7 B is trivial on the bus.
  - **Drained in small batches — do NOT reintroduce a large stack buffer.** `Navigation::Update()` is in the deepest periodic call chain (→ `InsEkf15::updateGps*` ~520–680 B) on a **2 KB stack** (`_Min_Stack_Size = 0x800`). A `Vec3f fifo_gyro[48]` (576 B) local pushed `Update()`'s frame to 992 B and **overflowed the stack** — observed as NaNs in the drained array and an `n` inconsistent with the valid data. Fixed by draining/integrating in 12-word batches (`kStrapdownFifoBatch`, looped to `kStrapdownFifoMaxBatches`), keeping the buffer at 144 B and `Update()` at ~568 B. Verify frame size via `Navigation.su` if this code changes.
